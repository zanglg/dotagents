# Specification

Use `assets/spec.md` as an outline for the requested `spec.md` or existing equivalent.

- State the problem, intended behavior, scope/exclusions, constraints, edge cases and observable acceptance criteria. Preserve stable REQ/AC IDs; append rather than renumbering established references.
- For an ordinary Feature, include only the technical approach and testing decisions needed to make it implementable. Label these separately from requirements so a solution choice is not mistaken for a user need. Add an optional technical-approach section to the template when useful.
- Link to an existing Design instead of duplicating it. When a separate Design is warranted, explain the reason and create it only within the requested synthesis scope.
- Keep uncertainty visible. Research and review may supply evidence; they do not turn proposals into approved requirements. Material unresolved needs can be clarified through `engflow-grill` when requested, or investigated through `technical-research`.
- Do not create tickets or an implementation ledger here. A user can give this Spec directly to `engflow-implement`, which owns task decomposition.
