# Empirical investigation

Running an experiment has a different write and execution scope from reading evidence. Establish the hypothesis, environment, commands, measurements, acceptance thresholds and time/resource bounds before execution. Reuse existing authorization; a request for a plan or discussion alone does not authorize running it.

- Run only authorized local commands and dependencies. Production modifications belong to the user's implementation workflow, not this investigation; deployment, destructive actions and external side effects require their applicable authorization. If the experiment cannot be isolated from important state, report the specific constraint instead of running it unsafely.
- Use a scoped temporary directory for disposable work. For durable reproducibility artifacts, use the user's location or established project convention within write authority; if neither exists, propose a location before writing. No Feature, prescribed root directory or ID scheme is required. Do not create or manage worktrees or switch branches. Use test fixtures, temporary data and the existing sandbox where appropriate; a directory alone does not isolate external side effects.
- Reuse the same PoC record for the same hypothesis/method and append meaningful trial results. Allocate IDs only when required by project conventions. When a durable record is warranted, adapt [the experiment outline](../assets/experiment.md) into one record holding hypothesis, environment/revision, commands, thresholds, measurements with units, failures, limitations and conclusion. Otherwise return these details in the conversation. Add scripts/small data only when needed for reproducibility; no mandatory separate results file.
- Choose the smallest experiment that can distinguish the competing explanations or invalidate a critical premise. Define the failure signal and check that the harness exercises the actual mechanism; use a known-negative/control case where practical to detect a vacuous pass. Separate harness/setup failures from evidence against the hypothesis. A minimal build, runtime probe or existing test may suffice; do not implement the whole feature merely to investigate it.
- Record relevant source/configuration and build/runtime commands, inputs, observed outputs and comparison conditions so the result can be reproduced. For timing or nondeterministic behavior, report repetitions, variability and sampling limits rather than treating one run as proof. Do not require seconds-long feedback when the real environment needs a bounded build or VM boot.
- An unexecuted experiment is `planned`; an attempted run with missing/inadequate evidence is `inconclusive` or failed, never passed. Preserve negative results. State what the result establishes and what it cannot: compilation is not runtime support, and mocked/emulated behavior is not verification of omitted hardware or concurrency properties. Avoid secrets and large raw logs.
- One writer owns the experiment output. Under a coordinating workflow, obey its exclusive-writer protocol; read-only research helpers do not perform experiment writes/runs. For standalone research, one bounded experiment may be delegated with explicit limits and exclusive output ownership under [the research delegation rules](context.md). Workers do not delegate further; the parent verifies outputs and consequential claims.
- Findings can support a design or ADR but cannot approve them. Report actual measured outcomes and uncertainty, then return to the research question. Existing `results.md` files remain valid historical evidence and are not deleted.
