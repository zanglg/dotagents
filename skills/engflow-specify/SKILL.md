# Engflow Specify

Turn effective intent into a **testable specification**. Start from a clear
request, discussion or existing Spec. No prior Clarify invocation or separate
artifact is required.

Use the [specification change method](references/specification-core.md):
identify the intended change, update affected behavior and acceptance together,
and check that the result is complete without drifting in scope. When a material
gap emerges, look up facts or ask the user within this task; do not restart it
as a separate stage.

Follow the [feature-record convention](references/feature-records.md) for path
selection, stable IDs, approval history and navigation. Write only on a clear
create/save/change request or an existing scoped grant. A confirmed decision
or pause alone is not permission; clarify ambiguous action or target before
editing. A preview stays in conversation.

Do not choose the technical solution, execute experiments, edit downstream
sources, create unrequested artifacts or manage Git state. Method reuse does
not add authority or invoke another Skill.

Report the Spec path or preview, material changes and validation findings,
and any remaining decisions or unverified assumptions. A quality check is
not user approval or proof of feasibility.
