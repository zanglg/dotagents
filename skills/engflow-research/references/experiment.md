# Empirical investigation

Running an experiment has a different write and execution scope from reading evidence. Establish the hypothesis, environment, commands, measurements, acceptance thresholds and time/resource bounds before execution. Reuse existing authorization; a request for a plan or discussion alone does not authorize running it.

- Run only authorized local commands and dependencies. Production modifications belong to `engflow-implement`; deployment, destructive actions and external side effects require their applicable authorization. If the experiment cannot be isolated from important state, report the specific constraint instead of running it unsafely.
- Use a scoped temporary directory or `engflow-doc/<FEAT>/experiments/POC-###-slug/` when durable evidence is requested or needed for the study. Do not create or manage worktrees or switch branches. Use test fixtures, temporary data and the existing sandbox where appropriate; a directory alone does not isolate external side effects.
- Reuse the same PoC record for the same hypothesis/method and append meaningful trial results. Allocate a new unused ID for a genuinely different experiment. One `experiment.md`, adapted from `assets/experiment.md`, holds hypothesis, environment/revision, commands, thresholds, measurements with units, failures, limitations and conclusion. Add scripts/small data only when needed for reproducibility; no mandatory separate results file.
- An unexecuted experiment is `planned`; an attempted run with missing/inadequate evidence is `inconclusive` or failed, never passed. Preserve negative results. Avoid secrets and large raw logs.
- One writer owns the experiment output. During implementation, only its currently designated writer (parent or granted implementation worker) performs authorized writes/runs; research/review helpers remain read-only. Outside implementation, one bounded experiment may be delegated with explicit limits and exclusive output ownership. Workers do not delegate further; the parent verifies outputs and consequential claims.
- Findings can support a design or ADR but cannot approve them. Report actual measured outcomes and uncertainty, then return to the research question. Existing `results.md` files remain valid historical evidence and are not deleted.
